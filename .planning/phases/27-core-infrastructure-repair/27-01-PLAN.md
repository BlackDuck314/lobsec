# Plan 27-01: Portullama Reconnection + Memory Search

**Requirements:** REPAIR-01, REPAIR-03
**Estimated scope:** Medium — diagnose remote auth, update proxy if needed, verify embeddings

## Context

Portullama at `<SOVEREIGN_GPU_HOST>:11435` returns "Unauthorized" since ~Apr 1. The remote server (owned by user) added authentication. The proxy already sends `Authorization: Bearer <OLLAMA_API_KEY>` to Portullama — the key is stored in HSM (`ollama-api-key` label).

Memory search uses BGE-M3 embeddings routed through the same proxy to Portullama (`/v1/embeddings` → Portullama `/api/embeddings`). It's configured in openclaw.json with `provider: "openai"`, `model: "bge-m3:latest"`, routing through the proxy.

## Steps

### 1. Diagnose Portullama auth requirement

```bash
# Test direct connectivity (bypass proxy)
curl -s http://<SOVEREIGN_GPU_HOST>:11435/api/tags 2>&1 | head -5
curl -s -H "Authorization: Bearer $OLLAMA_API_KEY" http://<SOVEREIGN_GPU_HOST>:11435/api/tags 2>&1 | head -5
```

Determine:
- Does the server respond at all? (network/firewall issue vs auth issue)
- Does the existing Bearer token work? (maybe just needs different format)
- What auth does the server expect? (check if Ollama was configured with `OLLAMA_API_KEY` env var)

### 2. Fix authentication (based on diagnosis)

**If token is wrong/expired:**
- Get correct token from user (they own the remote server)
- Store new token in HSM: `pkcs11-tool --write-data <file> --label ollama-api-key`
- Regenerate `.env.proxy` by restarting lobsec service (HSM extraction runs on start)

**If Ollama was reconfigured with different auth mechanism:**
- Update proxy's Ollama provider config to match (Bearer vs Basic vs custom header)
- May need to update `llm-router.ts` authPrefix

**If server is unreachable (network/firewall):**
- Ask user to check remote server status
- Document as external dependency

### 3. Verify Portullama routing end-to-end

```bash
# Through proxy
curl -sk -H "Authorization: Bearer <gateway-token>" \
  -H "Content-Type: application/json" \
  -d '{"model":"qwen2.5:32b","messages":[{"role":"user","content":"Say hello"}]}' \
  https://127.0.0.1:18790/api/chat
```

Confirm:
- Proxy forwards to Portullama successfully
- Response contains model output
- Sovereign routing works via Telegram (`/sovereign` command)

### 4. Verify memory search embeddings

```bash
# Test embedding endpoint through proxy
curl -sk -H "Authorization: Bearer ollama-local" \
  -H "Content-Type: application/json" \
  -d '{"model":"bge-m3:latest","input":["test query"]}' \
  https://127.0.0.1:18790/v1/embeddings
```

Confirm:
- BGE-M3 returns embedding vectors
- OpenClaw memory search initializes without errors on gateway restart
- Semantic search returns results via Telegram

### 5. Update proxy source if code changes were needed

If `llm-router.ts` or `server.ts` were modified:
- Build: `cd /root/lobsec && pnpm build --filter @lobsec/proxy`
- Deploy: `cp packages/proxy/dist/* /opt/lobsec/proxy/`
- Clear compile cache: `rm -rf /tmp/node-compile-cache`
- Restart: `systemctl restart lobsec-proxy`

## Success Criteria

1. `curl http://<SOVEREIGN_GPU_HOST>:11435/api/tags` returns model list (with auth)
2. Sovereign routing via proxy returns LLM response from qwen2.5:32b
3. `/v1/embeddings` with bge-m3:latest returns embedding vectors
4. OpenClaw memory search initializes cleanly (check journalctl for memory errors)

## Risk

- Remote server may be permanently reconfigured/offline — user input needed
- If Ollama version changed, API may have breaking changes
- Memory search SQLite may need reindexing if embeddings were partially corrupted
