# Plan 27-02: Jetson CF-Access Reconnection

**Requirements:** REPAIR-02
**Estimated scope:** Medium — diagnose CF-Access 403, update credentials if needed

## Context

Jetson inference at `<JETSON_HOSTNAME>` returns HTTP 403 (CF-Access denied). TLS handshake succeeds (TLSv1.3, resolves to 104.21.96.24 via Cloudflare). The proxy has CF-Access credentials in `.env.proxy`:
- `JETSON_CF_CLIENT_ID="REDACTED_CF_ACCESS_CLIENT_ID"`
- `JETSON_CF_CLIENT_SECRET="REDACTED_CF_ACCESS_SECRET"`

The proxy injects these as `CF-Access-Client-Id` and `CF-Access-Client-Secret` headers via `extraHeaders()` in `llm-router.ts`. The deployed code has baseUrl hardcoded to `https://<JETSON_HOSTNAME>`.

Models: gemma3:1b, llama3.2:3b, qwen2.5-coder:3b.

## Steps

### 1. Diagnose CF-Access rejection

```bash
# Test with current credentials
curl -s -o /dev/null -w "%{http_code}\n" \
  -H "CF-Access-Client-Id: REDACTED_CF_ACCESS_CLIENT_ID" \
  -H "CF-Access-Client-Secret: REDACTED_CF_ACCESS_SECRET" \
  https://<JETSON_HOSTNAME>/api/tags

# Check response body for CF error details
curl -s \
  -H "CF-Access-Client-Id: REDACTED_CF_ACCESS_CLIENT_ID" \
  -H "CF-Access-Client-Secret: REDACTED_CF_ACCESS_SECRET" \
  https://<JETSON_HOSTNAME>/api/tags 2>&1 | head -20
```

Determine:
- Is the CF-Access service token expired? (tokens have configurable lifetime)
- Was the CF-Access application reconfigured? (new policy, new service token)
- Is the Ollama service behind CF even running?

### 2. Fix credentials (based on diagnosis)

**If CF-Access token expired:**
- User creates new service token in Cloudflare Zero Trust dashboard
- Store new credentials in HSM:
  ```bash
  echo -n "<new-client-id>" > /tmp/jetson-cf-id
  echo -n "<new-client-secret>" > /tmp/jetson-cf-secret
  SOFTHSM2_CONF=/opt/lobsec/boot/softhsm2.conf pkcs11-tool \
    --module /usr/lib/softhsm/libsofthsm2.so \
    --token-label lobsec --pin <pin> \
    --write-data /tmp/jetson-cf-id --label jetson-cf-client-id --type data
  # Same for secret
  rm /tmp/jetson-cf-id /tmp/jetson-cf-secret
  ```
- Restart lobsec service (HSM extraction regenerates .env.proxy)

**If CF tunnel is down:**
- Ask user to check Cloudflare tunnel status for <JETSON_HOSTNAME>
- This is an external dependency — document and move on

**If CF-Access policy changed (IP restriction, mTLS, etc.):**
- Ask user to check CF-Access application settings
- May need to add server's IP to allowed list

### 3. Verify Jetson routing end-to-end

```bash
# Through proxy
curl -sk -H "Authorization: Bearer <gateway-token>" \
  -H "Content-Type: application/json" \
  -d '{"model":"gemma3:1b","messages":[{"role":"user","content":"Say hello"}]}' \
  https://127.0.0.1:18790/api/chat
```

Confirm:
- Proxy forwards to <JETSON_HOSTNAME> with CF-Access headers
- Response contains model output from gemma3:1b
- All 3 Jetson models respond

### 4. Sync source with deployed code

The deployed `llm-router.js` has `https://<JETSON_HOSTNAME>` hardcoded but the source uses `JETSON_BACKEND_URL` env var with fallback to `https://localhost:11434`. Update source to match deployed:

```typescript
// In packages/proxy/src/llm-router.ts
baseUrl: process.env["JETSON_BACKEND_URL"] ?? "https://<JETSON_HOSTNAME>",
```

Build and redeploy if other changes were made.

## Success Criteria

1. `curl` with CF-Access headers to `<JETSON_HOSTNAME>/api/tags` returns 200
2. All 3 Jetson models (gemma3:1b, llama3.2:3b, qwen2.5-coder:3b) respond through proxy
3. Source code `llm-router.ts` matches deployed behavior

## Risk

- CF-Access token may need user intervention (Cloudflare dashboard access)
- Jetson device (NVIDIA Jetson) may be offline/powered down
- CF tunnel may have been removed entirely — user confirmation needed
