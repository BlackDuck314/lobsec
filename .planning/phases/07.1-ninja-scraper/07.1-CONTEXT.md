# Phase 7.1: Ninja Scraper - Context

**Gathered:** 2026-03-12
**Status:** Ready for planning

<domain>
## Phase Boundary

Build a **general-purpose Python scraping engine** (`@lobsec/scraper`) for the lobsec ecosystem — NOT specific to UAE real estate. It's a top-level capability that any future project can use. Then rewrite all 7 UAE RE collectors as Ninja Scraper missions, proving the engine works end-to-end. All future collectors (Phases 8-9, 22 more sources) will also use Ninja Scraper missions.

The engine uses Crawlee for Python with PlaywrightCrawler for orchestration, Patchright (undetected Playwright fork) for stealth browsing, mission-based YAML specs for declarative source definitions, and a FastAPI API layer for service access.

This phase replaces the failed TypeScript collectors from Phase 7 (all 7 failed against real websites — WAF, CAPTCHA, CloudFront 403).

</domain>

<decisions>
## Implementation Decisions

### Architecture & Package Layout
- New top-level `@lobsec/scraper` package at `packages/scraper/` — peer to `@lobsec/shared` and `@lobsec/uae-re`
- General-purpose scraping engine — NOT hardcoded for real estate or fixed sources
- Any part of the lobsec ecosystem can use it for any scraping need
- UAE RE collectors are consumers of the scraper API, not part of the scraper itself

### Collection Ownership
- Python owns collection entirely — Crawlee/FastAPI handles scheduling, concurrency, retries, browser pool
- TS CollectorRegistry becomes a thin wrapper that calls the Ninja Scraper HTTP API
- SourceCollector base class (TS) no longer does the actual scraping — just triggers API calls and reads results
- Existing Python normalization modules (normalize_dld.py, etc.) stay in `packages/uae-re/python/` — they process raw files output by the scraper. Clean separation: scraper collects, normalizers transform

### TS Collector Fate
- Delete all 7 TypeScript collector implementations (dld-sales.ts, ejari-rentals.ts, building-permits.ts, adrec-abu-dhabi.ts, bayut-listings.ts, propertyfinder-listings.ts, dewa-connections.ts)
- Domain knowledge (URLs, field mappings, selectors) transfers to YAML mission specs
- SourceCollector base class and CollectorRegistry may be refactored to thin API clients

### Mission Specs
- YAML files in `packages/scraper/missions/` — one per source
- Human-readable, version-controlled, easy to add new sources
- Ninja Scraper loads missions at startup
- All future collectors (Phases 8-9, 22 Tier B/C sources) will be YAML mission files

### Phase Scope
- Build the complete scraper engine (Crawlee, Patchright, FastAPI, mission framework)
- Rewrite all 7 UAE RE collectors as Python missions
- Prove end-to-end: scrape → raw file → normalization → SQLite
- Phase 7 effectively becomes complete once this works

### Integration Model
- TS plugin talks to Ninja Scraper via HTTP API on localhost
- FastAPI endpoints: /scrape, /crawl, /missions (Firecrawl-inspired)
- Token authentication on API (Bearer token from HSM) — consistent with gateway/proxy pattern

### Stealth Stack
- Patchright (undetected Playwright fork) for browser automation
- Conservative defaults: max_concurrency=2, 2-6s random delays, exponential backoff
- No proxy rotation initially — start with Patchright stealth + delays
- Add residential proxy support later if sites start blocking
- Anti-bot handling: graceful 403/CAPTCHA detection, skip and alert (no aggressive retry)

### Deployment & Operations
- Own Python venv at `/opt/lobsec/scraper-venv/` — isolates Crawlee/Patchright/FastAPI from analytics-venv (pandas/statsmodels)
- Always-running systemd service: `lobsec-scraper.service`
- Port: 18791 (loopback only) — follows sequence: gateway=18789, proxy=18790, scraper=18791
- Browser pool pre-warmed for fast response
- Same systemd hardening as other services (NoNewPrivileges, ProtectSystem=strict)

### Claude's Discretion
- FastAPI endpoint design (request/response schemas)
- YAML mission spec schema (fields, validation, defaults)
- Crawlee crawler configuration and request queue management
- Patchright launch options and fingerprint settings
- Error handling and failure reporting format
- Internal Python package structure within packages/scraper/
- How the thin TS CollectorRegistry wrapper calls the API
- Raw file output format per mission (CSV, JSON, HTML snapshots)

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `runPython()` bridge (`packages/uae-re/src/analytics/bridge.ts`): Can be adapted for calling Ninja Scraper API, or kept for normalization-only Python calls
- Python normalization modules (`packages/uae-re/python/uae_re/normalize_*.py`): Stay as-is, process raw files from scraper output
- Pandera schemas (`packages/uae-re/python/uae_re/schemas/`): Validate normalized data — unchanged
- `CircuitBreaker` + `retryWithBackoff` (`@lobsec/shared`): Could be used in the thin TS wrapper around scraper API calls
- Playwright already installed at system level for Examy QA — Patchright will need separate installation
- HSM credential pattern: token auth for new service follows same `pkcs11-tool` + env var pattern

### Established Patterns
- Loopback-only services with token auth (gateway:18789, proxy:18790)
- systemd hardened units with ExecStart bash wrapper to source .env
- Plugin tools call localhost services (existing pattern from proxy wiring)
- fscrypt encryption on data directories

### Integration Points
- FastAPI service at 127.0.0.1:18791 — new systemd service `lobsec-scraper.service`
- HSM: new `scraper-auth-token` data object for API auth
- nftables: scraper service needs egress access to all source domains
- Raw data output: `/opt/lobsec/data/raw/` (existing directory, fscrypt encrypted)
- TS plugin: CollectorRegistry refactored to HTTP client calling scraper API
- Normalization: existing Python modules read raw files from scraper output path

</code_context>
